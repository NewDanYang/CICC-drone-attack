# 任务要求

## CICC 无人机项目 Stable RC1 工程集成与验收说明

**目标分支：** `release/stable-rc1`  
**整理日期：** 2026-11-01  
**文档依据：** 用户分段提供的任务要求。本文记录待执行要求，不代表代码已集成、服务器已部署或验收已通过。

## 一、任务目标

本轮工作不再以增加新功能、开展新算法研究或提升模型能力为目标，而是整合此前已经完成且有实验依据的基础比赛功能，形成一套稳定、可复现、符合比赛规则的六阶段无人机执行系统。

Stable RC1 应当具备：

1. 使用官方指定的自然语言指令，通过 FM9G 模型完成语义解析。
2. 支持比赛要求的逐阶段输入、执行与状态确认。
3. 稳定完成起飞、正向穿框、二维码识别、反向穿框、指定颜色气球击破、返航降落六阶段。
4. 保留已验证的安全恢复、目标跟踪、视觉伺服、规划导航和速度修正成果。
5. 在同一套冻结代码及运行参数下，通过红、紫、蓝三色多轮完整仿真验收。
6. 完成规则合规检查，提供足以复核每次试验结果的原始证据。
7. 最终形成可部署、可回滚、具有明确版本身份的 Stable RC1 发布包。

**核心原则：** 先确保基础比赛系统可靠，再将九格视觉和创新规划作为后续独立升级模块。

Stable RC1 不承担九格视觉识别加分或独立路径规划创新加分的验收目标，但必须保留规则要求的 FM9G 自然语言语义解析功能。

研究代码可以保留在仓库中，但不能启用、覆盖稳定链路或被计入 RC1 的运行验收。

## 三、集成实施步骤

### 阶段 A：建立独立集成分支

从 `main` 创建 `release/stable-rc1`。

在该分支中引入 PR #24 的必要变更，包括运行源码、依赖配置、测试工具、发布清单和相关实验记录。

本阶段不直接修改 `main`，也不在尚未验收时关闭稳定性回退路径。

集成时重点检查：

- `mission_once.py` 与 `bt_ros.cpp` 的任务协议是否一致。
- TargetTracker、VisualServo 及相关插件是否配套。
- WaitForStablePosition 等行为树节点是否正确注册。
- PlanningControl、GoTo、安全恢复逻辑是否完整。
- 启动脚本、ROS overlay、插件加载路径和配置参数是否一致。
- 历史速度补丁是否已经体现在实际运行源码中。

不得采用简单覆盖整个旧工作区的方式处理集成。

### 阶段 B：构建与静态验证

使用独立或可恢复的 ROS 工作区完成构建，执行 PR #24 随附的离线测试及 ROS 隔离测试。

确认：

1. 代码能够完整编译。
2. 行为树所需节点全部注册，六阶段任务均可构造。
3. ROS 话题、服务及插件接口一致。
4. 实际加载的程序和动态库与待验收源码一致。
5. 没有同时加载互斥的九格新 Tracker 和传统 Tracker。
6. 关键速度、安全和规划参数符合冻结配置。

**特别要求：** 必须检查正在运行的二进制与动态库身份。仅通过 Git SHA、磁盘文件哈希或编译成功不能证明正在运行的就是本次候选。

静态与隔离测试通过后，才能进入完整仿真。

## 四、冻结速度与运行参数

| EGO-Planner `optimization/max_vel` | 0.30 m/s |
| EGO-Planner `bspline/limit_vel` | 0.30 m/s |
| VisualServo `forward_velocity` | 1.00 m/s |
| VisualServo `sprint_velocity` | 1.50 m/s |

以上为 PR #24 已记录的运行配置。执行时必须核对真实 ROS 参数、行为树传参及实际加载代码，而非仅检查配置文件默认值。

蓝色气球历史专用的 `blue_sprint_velocity=1.0` 分支已经不属于当前计划采用的统一冲刺配置；必须确认没有通过旧源码或旧插件重新引入。

禁止为了缩短用时而擅自调整仿真倍率、物理步长、渲染参数、飞行限速或安全边界。

如果发现当前实际运行版本与上述配置不一致，应先记录差异并确认来源，不得直接将未知状态标记为合规通过。

## 五、真实仿真回归测试

### 5.1 测试环境

使用比赛对应的正式 ROS、PX4/MAVROS 和仿真场景链路进行实际执行，不使用纯 Mock 或离线行为树测试代替完整仿真。

每次试验必须：

- 启用真实 FM9G 语义解析。
- 使用组委会指定的官方指令原文。
- 按比赛要求逐阶段输入，等待当前阶段确认后再执行下一阶段。
- 使用实际感知、规划与控制链路。
- 在全新且正确初始化的三气球场景中测试。
- 保存完整执行视频、ROS 日志、遥测及判定依据。

允许使用自动化工具完成环境初始化、日志收集与统计，但不得用预制六阶段任务列表自动注入来代替正式的逐条自然语言输入。

### 5.2 最低测试矩阵

在同一套冻结源码、二进制和参数下，至少完成：

| 颜色 | 完整任务轮次 | 目标 |
| --- | ---: | --- |
| 红色 | 3 | 三局完整六阶段 |
| 紫色 | 3 | 三局完整六阶段 |
| 蓝色 | 3 | 三局完整六阶段 |
| 合计 | 9 | 三色完整回归 |

建议采用交错颜色顺序，避免环境运行时间、模型状态或场景变化造成系统性偏差。

测试之前冻结候选版本，不允许一边修改代码、一边将不同版本的试验累计为同一批九局结果。

### 5.3 单局记录内容

每局至少记录：

- 运行 ID、场景 ID、目标颜色。
- 源码提交 SHA、实际二进制及插件哈希。
- 官方自然语言指令与模型原始回答。
- 六阶段开始、结束、成功及失败状态。
- 气球初始数量、目标气球最终状态、非目标气球状态。
- 实际撞击或爆裂的视频证据。
- 完整任务用时与各阶段耗时。
- 安全边界触发、恢复事件、疑似墙体接触。
- 实际速度与控制量遥测。
- 降落状态及最终 `armed=false`。
- 模型、ROS 或规划器错误信息。

行为树 `SUCCESS`、Observer 的 `mission_success` 和气球实际击破必须分开记录。

尤其不得把 `ForceSuccess`、视觉目标消失或 `ATTEMPTED_UNVERIFIED` 自动解释为指定气球已被击破。

### 5.4 稳定版验收门槛

本轮采用以下目标作为 Stable RC1 的正式通过条件：

1. 红紫蓝各 3/3 完成规定六阶段。
2. 9/9 正确击破指定颜色气球，具有可核对证据。
3. 0 次确认误击，0 次同局错误删除其他气球。
4. 9/9 正常返航、降落并解除武装。
5. 0 次确认的违规物理碰撞；软件边界事件沿用此前不超过 1/9 的工程目标，同时逐次复核。
6. 无影响任务完整性的 ROS、行为树、模型或规划器异常。
7. 全部试验使用同一套候选版本及可核对的正式输入流程。
