# 5.6b 复核：第二次尝试无效，第一次尝试的停滞原因仍未查明

日期：2026-11-01（北京时间）。只读 Astra 提交 `bcdf4ec` 的证据（两次台架试验的 `trial_rosout.jsonl.gz`、`observer.out`、`mission_once.out`），没有连接服务器（见文末"当前阻塞"）。

## 结论

1. **第二次尝试（30/30 紫色）不是独立试验，不能作为"30px 是否收敛"的证据，Astra 报告里已经正确地没有把它当证据用，但原因可以查得更具体：这局复用了第一次尝试残留的仿真/行为树状态，不是环境没有重置导致的巧合。**
2. **第一次尝试（20/20 红色）本身是真实的、独立的停滞**：无人机在前置导航阶段卡在距目标 `(4.3, 1.0, 0.7)` 约 2.5 m 处，持续 220 秒以上。但 `deadzone_yaw`/`deadzone_vz` 只影响 VisualServo 节点，这次停滞发生在 VisualServo 启动**之前**（还在 GoTo/TargetLocator 阶段），补丁本身不太可能是原因。真正原因尚未查明，需要服务器访问才能继续排查。
3. `(4.3, 1.0, 0.7)` 是红色 A 区的冻结部署航点（`v3_stability/reports/hit_balloon_part1_final/REPORT.md`：`approach_pos` A/B/C 分别为 `4.3;1.0;0.7`、`4.3;-2.0;0.7`、`5.3;1.0;0.7`），不是本次实验引入的新坐标。

## 1. 第二次尝试为什么无效：直接证据

`5_6b_a30/trial_rosout.jsonl` 开头几行（观测器自己的 `run_start` 之后几十毫秒内）：

```
07:45:48.302  [ArucoDetectNode] Detection auto-disabled after success (saving CPU)
07:45:48.344  mavros_state: connected=True armed=True mode=OFFBOARD
07:45:48.352  observer_ready mode=no_launch_llm waiting_for=/mission_command
...
07:45:49.12   [checkArrival] odom=(3.07,-1.08,0.91) target=(4.30,1.00,0.70) dist=2.430
...
07:46:12.209  mission_start source=/mission_command   ← 这局自己的任务真正开始的时间
```

也就是说：**这局观测器自己的计时器开始跑的那一刻，无人机已经是解锁状态、已经在 OFFBOARD、ArUco 已经"成功后自动关闭"、而且已经在向 `(4.3,1.0,0.7)` 做 checkArrival——这些全部发生在这局自己的 `/mission_command` 真正发出（07:46:12）之前 23 秒**。这不可能是这局紫色任务自己产生的状态，只能是上一局（20/20 红色）结束时残留的行为树/仿真状态：红色那局自己的 BT 卡在 GoTo 里超时退出（观测器判定超时，不是 BT 正常完成），而真正执行树的 `bt_ros` 进程、仿真环境（PX4/RflySim3D）、无人机的物理位置都没有被重新启动，只有 `mission_once.py`（生成新指令的那个 Python 入口）被重新跑了一遍、发了一条新的 `/mission_command`。旧的行为树大概率还卡在上一局的 GoTo 节点里，没有空出来接收新指令，所以紫色任务实际上从未真正开始执行（没有任何 `[GoTo]`、`[Takeoff]` 相关的新日志）。

`--no-launch-llm` 本身是 `baseline_tools/run_baseline.py` 里一个正常、文档化的观测器参数（表示"谁调用 `mission_once.py` 由调用者自己负责，观测器只负责计时和记录"），这个参数本身不是问题；问题是**在两次尝试之间，仿真环境（`bt_ros`/PX4/RflySim3D）没有完整重启**，只重启了模型推理进程。

Astra 的报告已经正确地没有把第二次尝试的"结果"当证据使用（报告原话："不能把这两局解释成'20px 不收敛'或'30px 不收敛'"），这一点判断是对的；这里只是把原因从"原因不明"补充成"可以具体指出是环境未重置"。

## 2. 第一次尝试的停滞：真实，但原因未知，且很可能与本次改动无关

`5_6b_a20` 是这组实验里唯一一次真正独立的试验：从 `07:36:43`（`/mission_command` 发出）到 `07:37:59`（第一次 `checkArrival` 显示目标 `(4.30,1.00,0.70)`），`takeoff`、穿框、ArUco、回穿全部正常完成（约 76 秒，和 5.5 阶段 C 那次红色实飞的时间量级一致）。之后无人机在 `(2.87–2.92, -1.05– -1.14, 0.86–0.91)` 附近持续徘徊，始终到不了 `x=4.3`，直到 300 秒超时。

**这次停滞发生在 VisualServo 启动之前**，`deadzone_yaw`/`deadzone_vz` 这两个参数只在 VisualServo 内部使用，GoTo/TargetLocator 阶段完全不会读取它们。所以：

- 这次停滞**不太可能是容差补丁本身造成的**（补丁只改了两个数字，没有改任何会在这个阶段执行的代码路径）；
- 但也**不能排除**是本次实验间接造成的，比如：补丁触发了一次 `catkin_make` 重新编译，编译/部署过程中环境被某种方式干扰；或者模型常驻显存/CPU占用让同时运行的规划器（ego-planner）响应变慢，导致原本能走到的路径走不动。这只是一个有待验证的假设，不是结论。
- `(4.3,1.0,0.7)` 本身是冻结部署航点，历史上是否也会偶发卡在这里，目前没有查到本地缓存的历史记录能直接证实或证伪（本地几份 `baseline_runs*.csv` 缓存里没有搜到 "checkArrival made no progress" 这条日志格式，可能是因为这条诊断日志是后来加的，旧记录格式不同，不能说明历史上从未发生过）。

## 4. 建议的下一步（服务器恢复后执行，交接见 `docs/astra-handoff-fm9g-visualservo-tolerance-retry.md`）

1. **先做一次对照，不改任何代码**：用冻结版 `visual_servo.cpp`（`a63b57fa...`）、已部署的阶段 B/C 候选 runtime，完整重启一遍仿真环境（`cleanup_sim.sh` 之后重新 `start_sim_environment.sh`），跑一局红色。如果这次仍然卡在 `(4.3,1.0,0.7)`，说明停滞和容差补丁无关，是环境或资源争用问题，需要转给负责规划/环境的方向（不在本项目组范围内，见 `AGENTS.md` §9 的目录划分）。如果这次顺利进入 VisualServo，再重新安排 20px/30px 的容差台架。
2. **每次台架之间必须完整重启仿真环境**，不能只重启模型进程或只重新编译 VisualServo 插件。`cleanup_sim.sh` 已经具备杀掉 `bt_ros`/`mavros_node`/`px4`/`RflySim3D`/`roscore` 的能力，要求每次台架前都执行一遍，而不是仅在"回滚"时使用。
3. 不要用本次两局的任何数字作为 20px/30px 收敛与否的证据，Astra 报告里的判断是对的，继续保持。
