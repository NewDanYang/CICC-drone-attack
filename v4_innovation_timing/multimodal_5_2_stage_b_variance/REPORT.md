# 5.2：阶段 B 为什么停——不是接入错了，是实时系统本身方差很大

日期：2026-11-01（北京时间，服务器时间 UTC 2026-10-31 16:xx）。只做离线录制帧回放，没有起飞，没有修改 Astra 阶段 B 的候选代码或部署状态。本报告诊断她停下的原因，并给出一个比她原有验收门更合适、但结论更谨慎的新证据。

## 结论先说

Astra 用的验收门（录制帧回放发布框 vs 离线 P12e 脚本发布框，逐帧中心差 ≤3 px）**过严**：这是在要求一个真实多线程、真实 GPU 延迟的系统和一个单线程、固定延迟虚拟时钟的仿真脚本逐帧位级对齐，两者的扫描触发帧天然会因几十毫秒的真实延迟抖动而错开一帧，之后 CSRT 各走各的路。所以我一开始怀疑"接入本身没问题，只是比较方式太严"。

**但把同一条真实录制序列重复跑 3 遍后，这个怀疑被推翻了**：真实 runtime 对同一个 05/09/13 三个局的定位准确率本身就有很大的局间方差，其中红色一次出现了接近失能的崩溃（19.1%），而另外两次在同样代码、同样数据下稳定在 68.1%。**问题不是"验收门选错了"，是"这套实时状态机本身不够稳，不能只跑一次回放就下结论"**。Astra 在证据不足、无法区分"接入 bug"和"正常统计噪声"时选择停下，这个判断本身是对的；只是她当时用来验证的单次回放结论同样不足以支持任何方向的判断，包括我最初以为的"其实已经可以"。

## 1. 为什么原验收门测的是错误的东西

阶段 B 报告里的 [`runtime_replay_score.json`](../multimodal_5_1_presence_flight/evidence/stage_b/runtime_replay_score.json)、[`scan_prompt_fix_smoke20_summary.json`](../multimodal_5_1_presence_flight/evidence/stage_b/scan_prompt_fix_smoke20_summary.json) 都是把真实 `PerceptionBridge`（两个真线程：`inference_loop` 做模型推理、`tracking_loop` 每 5 ms 轮询 CSRT）喂进录制帧，和单线程虚拟时钟的 `p12e_native_track.py` 逐帧比较发布框的像素坐标。

修复扫描插值和提示词映射两个真 bug 之后（这两个修复本身是对的，见下），20 帧 smoke 仍有 14.08 px 的最大中心差。我把这 20 帧的发布框和参照框分别对真实 YOLO 真值重新打分（而不是互相比较），结果：

```
runtime : centre 14/19 = 73.7%   precision 93.3%
offline : centre 14/19 = 73.7%   precision 93.3%
```

完全一致——说明两条轨迹虽然像素级不同，但"对不对"是一样的。于是我以为问题只是验收门选错了比较对象。

## 2. 但把全长局重复跑 3 遍，方差本身就是结论

用 [`tools/validate_runtime_vs_truth.py`](tools/validate_runtime_vs_truth.py)（同一个真实 `PerceptionBridge`，服务器部署的阶段 B 候选代码，不改一行）跑 05_r1_blue / 09_r2_purple / 13_r3_red 三个完整局（145/220/254 帧），发布框直接对该局原始 YOLO 真值打分，不经过 P12e 参照：

| 局 | 离线 P12e（单次） | 实测 run1 | run2 | run3 | 顺序 |
|---|---:|---:|---:|---:|---|
| 05 蓝 centre/precision | 78.1% / 92.6% | 75.0% / 88.9% | 75.0% / 88.9% | **84.4% / 96.4%** | 蓝在第 1/1/3 位 |
| 09 紫 centre/precision | 65.9% / 91.2% | 50.0% / 77.8% | 62.7% / 87.8% | 57.9% / 82.0% | 紫在第 2/2/2 位 |
| 13 红 centre/precision | 85.1% / 93.0% | 68.1% / 84.2% | **19.1% / 24.3%** | 68.1% / 84.2% | 红在第 3/3/1 位 |

run1 用 `validate_truth.log`、run2 用 `validate_truth2.log`（顺序：蓝→紫→红）、run3 用 `validate_truth3.log`（顺序：红→紫→蓝，用来排除"同进程里跑的第三个局必然更差"这个混杂因素）。三份完整 JSON 在 `evidence/run{1,2,3}_summary.json`。

**关键证据**：红色 run1 和 run3 的控制流事件计数逐项相同——决策次数 169、`track_invalidated` 152、`replay` 16、`acquire_tiles`/`track_sweep` 调用次数和延迟中位数都对得上小数点后三位——但 run2 同样是 169/152/16，**事件类型和次数也完全一样**，centre 却从 68.1% 掉到 19.1%。也就是说：高层状态机"什么时候搜索、什么时候跟踪、什么时候判失效"这件事是可复现的，但在某一次运行里，模型实际吐出的框坐标明显更差，导致 CSRT 从一个更偏的框开始追，此后整条轨迹发散。推测动作：

- GPU 是全组共用的单实例（`AGENTS.md` §9），某次推理可能被别的进程挤占导致个别调用延迟异常，错位的那一帧恰好把追踪器带偏；
- 或者 bf16 矩阵乘法在 GPU 上的规约顺序本身就不是逐 run 位级确定的，概率接近阈值的那次边缘判定刚好翻了一次，CSRT 对初始框很敏感，一次小偏差会被放大成持续发散。

这两个机制哪个是真正原因，本轮**没有分离验证**，不应该当作已证实的结论来引用。但现象本身是确凿的：同一套代码、同一批录制帧、同一次只改变运行顺序，红色局的发布精度在 24.3% 和 84.2% 之间摆动。

## 3. 和 Astra 的两个真 bug 修复无关

`track()` 的扫描插值 off-by-one（用 `positions[j-1]` 而不是 `[0.0]+positions` 做坐标轴，导致交点整体偏移并在最后一档越界）和提示词颜色映射（内部英文枚举直接拼进中文提示词）这两处修复是真实的、必要的——修复前的 `runtime_smoke_blue_audit_handoff_barrier.jsonl` 里有 8 次 `IndexError`，修复后 0 次。这两个修复应当保留，不需要重做。本报告发现的方差问题出现在修复**之后**，是另一层问题。

## 4. 结论对阶段 C 的意义

**不建议现在进入阶段 C 仿真飞行。** 不是因为候选代码有已知 bug（目前没有发现新 bug），而是因为：

1. 单次录制帧回放的结果不能代表这套实时状态机的真实表现——同一局可能是 68% 也可能是 19%；
2. 红色出现的崩溃模式（169 次决策里 152 次判失效，几乎全程停留在"搜索/重新获取"状态）如果在飞行里发生，意味着整个击球窗口期几乎拿不到有效像素位置，不是"稍微差一点"，是"这局等同没有视觉伺服"；
3. 没有做到 `AGENTS.md` §3.1 要求的"至少 3–5 局才能下判断"——阶段 B 原报告只跑了 1 次 20 帧 smoke，本报告跑了 3 次全长局，样本量依然偏小，只够发现方差存在，不够估计真实分布。

## 5. 建议的下一步（供 Astra/用户决定，本轮未执行）

- 在正式进入阶段 C 前，把"重复 N≥5 次同一录制局、报告中位数和最差一次"作为阶段 B 的硬性验收方式，而不是跑一次回放+改进验收门的像素阈值。
- 如果最差情况的崩溃频率不可接受，需要让状态机对"判失效"更保守：例如要求连续 2 次（而不是当前已有的 1 次负样本容忍）阴性才失效，或在重新获取后用更大的窗口/更低阈值做一次确认扫描，减少对单次模型输出的敏感度。这是工程改动建议，不是本轮已验证的修复。
- 如果怀疑是 GPU 共享导致个别调用延迟异常，可以在审计日志里记录每次调用的 CUDA 事件耗时分布（不只是壁钟延迟），用来和"低延迟/高延迟"调用是否对应"发散/不发散"做关联，而不是现在这样只能事后猜测。
