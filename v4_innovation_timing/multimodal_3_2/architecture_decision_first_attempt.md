# 九格多模态 3.2 架构决策

日期：2026-10-23
状态：10 月 23 日的实现前决策存档；10 月 25 日追加复审结论。本 PR 仅封存失败实现和证据。

> 最终决定：不采用本轮候选，保持封存部署。本轮传图契约实现错误，processor 实际收到 0 张图片；错误相机、旧帧处理和跟踪失效判据也未解决。故只能判定“实现未通过”，不能据红局否定九格模型或本架构。详见 [3.2 报告](REPORT.md)。

## 1. 规则和现状

我核对了仓库根目录的 `AGENTS.md`、`打击.pdf` 第 4.3 的评分表及第 4.4 的附加条款，并阅读了 `task3_1` 交接材料（该目录位于远端 `codex/task3-1-midterm-report` 分支）。规则表把“使用九格多模态大模型目标识别”列为 10 分加分项；4.4(5) 要求穿越障碍的感知结果在窗口中可见，缺少感知窗口扣 5 分，展示感知但没有用于控制再扣 5 分，并要求展示 bbox。规则还要求实时计算目标位置/估计，不能用预设轨迹代替。

当前气球闭环的 `TargetTracker` 订阅 `/objects`，其上游 `det_color.py` 使用 YOLO 检测 balloon，再用 HSV 分色，发布连续 `pixel_target` 给封存的 `VisualServo`。这条链路仍然是 YOLO 的目标识别路径。3.1 评测器的九格输出只有 `color` 和 `region(left/center/right)`，不能直接提供 PD 控制所需的连续像素框。3.1 交接报告还明确说明它是开发/诊断集，不是正式验收：原视角蓝色只有 14/20 帧独立可辨认，标签没有完全盲标，P50/P95 推理时延为 2.386/2.627 s。

## 2. 候选方案比较

### 候选 A：决策级九格 + 原 YOLO 跟踪

在接近点调用九格一次，使用其颜色/大致区域决定目标区；进入视觉伺服后仍让 `det_color.py` 输出像素位置。

* 优点：改动最小，九格时延不进入 10 Hz 伺服回路，容易保护 Part 1 的命中率。
* 风险：目标类别和连续位置实际仍由 YOLO 识别，九格只是一次性提示。官方 FAQ 明确说混合使用不能拿加分；评审复核代码时很容易认定违反“九格独立完成目标识别”。
* 决策：拒绝作为 3.2 加分候选。它可以作为不加分的安全回退，但不能作为本任务的验收实现。

### 候选 B：九格 bbox + 非语义跟踪器（选定）

在同一个 `mission_once.py` 模型实例中订阅 RGB 图像。气球阶段激活时，每次九格调用都输入完整图像并输出严格 JSON bbox（颜色、类别、`x1,y1,x2,y2`）；随后只用该 bbox 初始化/校正一个不含类别判断的光流/Kalman 跟踪器。跟踪器在九格调用之间发布上一次九格确认的目标框，超时则发布无效框，不调用 YOLO、不调用 HSV，也不从 `/objects` 读取 YOLO 结果。可视化窗口同时画九格 bbox、当前跟踪框、颜色和时间戳。目标选择日志记录 `model_frame -> selected_color/box -> published_pixel_target -> control`。

* 优点：九格是唯一的目标识别者；跟踪器只是对九格已经确认的目标做时间连续化，符合官方 FAQ“九格输出初始检测框后使用跟踪器”的允许路径。`VisualServo` 状态机和安全边界可以保持不变，改动集中在识别/目标选择层。
* 风险：2.4 s 级推理不能当作高频 PD。跟踪器只能在模型校正之间维持目标，遮挡、快速转动或模型 bbox 误差会使框漂移；3.1 蓝色证据不足，不能预先假设三色均可靠。必须设置最大保持时间和失效日志，不能把过期框当成新识别。
* 约束：气球激活期间要停用 YOLO 发布到 `/objects` 的气球结果，避免两条识别路径竞争；非气球阶段不改变封存的 YOLO/ArUco 链路。模型加载一次，不能在新节点复制 FM9G4B-V。

### 候选 B2：九格精确 bbox 直接低频修正，高频维持

只由九格输出归一化中心和尺寸；每次推理期间保持位置，返回后再做小幅修正，不引入目标跟踪器。其识别来源更简单，但 3.1 的秒级延迟不能直接替代现有 PD 输入；保持旧像素坐标也不是高频观测。要可靠实施需增加停等、状态确认和补偿控制节奏，会扩大已封存飞行逻辑的改动面。本轮不选，不能通过调大 data_timeout 来把陈旧输出伪装成实时反馈。

### 候选 C：九格低频区域决策 + 固定航向/位置动作

九格只返回三分区，行为树根据区域选择预先定义的几个动作，之后不做连续像素跟踪。

* 优点：不需要解析精细 bbox。
* 风险：区域只有三档，不能稳定提供命中所需的连续修正；固定动作也会接近规则禁止的预设轨迹，无法解释为实时感知控制。它既可能降低命中率，也不能作为可信的 4.4(5) 实现。
* 决策：拒绝。

## 3. 采用范围和止损门

本轮采用候选 B 进行最小可行性实现，但实现不是自动等于通过。先在本地完成 schema、线程/队列、窗口和审计日志，再做红/紫/蓝各一局窗口验证。只有同时满足以下条件才进入 3.3：

1. 每个颜色至少有一局真实图像推理，日志中有完整的九格原始 bbox、跟踪框、选色和实际 `/objects`/`pixel_target` 消费记录；
2. 九格 bbox 更新时延、保持超时和失效都有数字，窗口中能看到 bbox；
3. 气球阶段只存在九格发布的目标结果，YOLO/HSV 发布被停用，且代码路径可审计；
4. 三色窗口演示没有明显的错误目标选择或过期框控制。

任一门槛失败，就停止 3.2/3.3，不把“调用了模型”包装成加分通过；回退到封存 Part 1。3.3 仍需与未接入九格的封存版本红/紫/蓝各至少 3 局对照，不能用窗口单局推断成功率。本轮停止后没有开展这批验收。

复审补充：原计划缺少飞行前的真实传图、相机一致性和跟踪质量门。若重新投入，必须先证明 processor 确实收到图像、sensor1 几何一致、采集时间戳和结果过期判据正确、光流丢失能使输出无效，才能重新考虑实飞。schema 单测通过不能代替这些验证。

## 4. 规则覆盖缺口

PDF 4.3 表格本身没有按类别拆分该 10 分；仓库补充 `规则.txt` FAQ 5.4 明确要求全部识别，且允许九格初始 bbox 后接目标跟踪器。按保守口径，“全类别 + 九格独立识别”作为完整 10 分硬性门槛。本轮 3.2 只尝试气球目标选择；其他阶段仍使用原 YOLO/ArUco，所以即使气球局成功也不能宣称完整加分合规。4.4(5) 原文讨论穿框窗口；气球展示只是沿用其验收原则，不能自动替代穿框证据。后续须另做本赛项实际出现的障碍物、方框、起降标识等全类别证明，不能把提示词中列出类别视作完成。
