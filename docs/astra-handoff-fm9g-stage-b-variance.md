## 0. 背景：你停得对，但原因不是验收门，是真实方差

你用的验收门（真实 runtime 回放 vs 离线 P12e 脚本，逐帧中心差 ≤3 px）确实选错了比较对象——两个系统一个真多线程真延迟、一个单线程固定延迟虚拟时钟，天生没法像素级对齐。我改成让真实 `PerceptionBridge` 直接对原始 YOLO 真值打分，一开始看起来吻合得很好（20 帧 smoke 两边都是 73.7%），我差点就得出"可以进阶段 C"的结论。

**但把 05/09/13 三个局各自重复跑了 3 遍后，结论反过来了**：红色局（13_r3_red_baseline）在代码完全不变的情况下，定位准确率在 68.1%、19.1%、68.1% 之间跳；崩溃那次（19.1%）的内部状态机事件计数（决策次数、判失效次数、调用类型分布）和两次正常的（68.1%）**逐项相同**，说明不是走错了逻辑分支，是某次模型输出的框坐标本身更偏，之后 CSRT 从错的地方开始追、一路发散。原因没有分离验证，可能是 GPU 共享被挤占导致个别调用延迟异常，也可能是 bf16 数值在不同次运行里不完全确定、刚好翻转了一次边缘判定。

结论：**你的候选目前没有发现新的逻辑 bug，两处真 bug 修复（扫描插值 off-by-one、颜色提示词映射）都是对的，保留**。但这套实时状态机本身的表现方差很大，单次或少数几次录制帧回放不足以判断能不能进阶段 C。

## 2. 任务 A：给每次模型调用加 GPU 侧计时（预算 0.5 天）

目的：区分"某次调用确实被挤占延迟异常"和"延迟正常但数值结果偏了"这两种可能，而不是像本轮一样事后只能猜。

在 `v2/presence.py` 的 `NativePresenceSweep.call()` 里，除了现有的 `time.monotonic()` 壁钟耗时，用 `torch.cuda.Event` 加一对 GPU 侧计时（`start.record(); ...; end.record(); torch.cuda.synchronize(); gpu_ms = start.elapsed_time(end)`），连同 `torch.cuda.memory_allocated()` 一起写进 `presence_model_call` 审计事件。不要改变调用本身的行为或返回值，只加测量。

## 4. 判断标准

对每个颜色，统计 5 次独立运行的 centre_pct 分布：

- **中位数** 需要 ≥ 对应颜色在 `multimodal_5_0_presence_sweep` 单帧测试中的准确率的 80%（红色基准约 85%、紫色约 64%、蓝色约 78%，所以中位数门槛分别约为 68%/51%/62%）；
- **最差一次** 不得低于 30%（对应"整局基本失能"的量级，用 19.1% 这次崩溃做参照，30% 作为留有余地的安全线）；
- 如果 GPU 侧耗时（任务 A）显示崩溃那几次伴随着明显更长或更不规则的调用延迟，记为"疑似资源竞争"；如果延迟正常但结果仍然偏差很大，记为"疑似数值不确定性"。两种情况都要如实分开报告，不要因为分不清就笼统写"原因不明"而不给任何倾向性判断。
