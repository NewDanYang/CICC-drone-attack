## 〇、这次任务顺序为什么和计划文档不一样，以及一个我从你的数据里挖出的线索

`docs/next-phase-plan-v2.md` 原计划是"1.5 先把刹车判据扩展到 APPROACHING，1.6 再查误击根因"。
**这次反过来**：先查根因（不占服务器），再决定该写什么代码，理由有两个：

1. 误击（多删一个非目标球）和"碰了没刹车"是两件可能完全不同的事。先把 SPRINTING 的判据
   原样搬到 APPROACHING，如果误击的真正原因是接近轨迹物理上离非目标球太近，这个代码改动
   根本碰不到病灶，白白用掉一次服务器上的编译+9 局验收。
2. **我翻了你已经下载到本仓库的证据，发现一个你的报告里没点出来的细节，可能会改变整个
   调查方向**：

   把 1.1 和 1.3 里"多删一球"的全部 5 个真实局（1.1 的 `batch1/r1_blue_a1`、
   `batch2/r1_purple_a1`；1.3 的 `batch1/r2_purple_a1`、`batch1/r2_blue_a1`、
   `batch1/r3_blue_a1`）的 `scene_snapshots.jsonl` 按时间点摊开看，Actor 数的变化
   分三种模式，**不是同一件事**：

   | 模式 | 局 | 现象 |
   |---|---|---|
   | A：试验结束时已经少两个 | 1.1 批次 2 紫球、1.3 的 r2 紫球、r2 蓝球 | `after` 快照就已经是 1（3→1） |
   | B：试验刚结束少一个，settle 期间又消失一个 | 1.1 批次 1 蓝球 | `after`=2，约 30–70 秒后的 `late` 快照才变成 1 |
   | C：试验结束时三个都还在，之后很快掉两个 | 1.3 的 r3 蓝球 | `after`=3，但**第一次** `late`（约 15–20 秒后）就已经是 1 |

   这三种模式的共同点：**气球不会无缘无故消失**，UE 的 `BP_Balloon_C` 一定是被某次碰撞
   触发了销毁逻辑，只是 Actor 列表反映这件事的速度不一样。1.2 已经验证过：不强制 `obj gc`，
   普通模式下 Actor 数更新可以晚 20 秒以上（1.2 报告里控制局就是 19.981 秒）；强制 GC 后可以
   压到 0.9 秒以内。**也就是说：模式 B、C 很可能不是"settle 期间凭空又死了一个"，而是这个
   非目标球早就被碰撞触发了销毁，只是常规采样没能及时发现**——真正发生碰撞的时刻可能比我们
   以为的更早，甚至可能和目标球是同一次接近/冲刺过程中蹭到的。

   **这意味着现在的误击统计（1.1 的 2/9、1.3 的 3/9）很可能是低估，而不是高估**：如果连
   125 秒的 `settled` 快照都可能还没等到某次碰撞的 GC 窗口，那么有些局的误击可能到现在都
   没被发现。这是本次调查要优先确认或排除的第一件事。

## 二、1.5（原计划编号不变，但内容是"误击根因排查"）：完全离线，先做这个

**不需要 SSH，不需要服务器，直接在本地用已经下载的证据工作。**

### 第一步：先确认模式 B/C 是不是"延迟发现的早期碰撞"，而不是别的东西

用现有的本地证据，不是去问服务器：

```bash
cat v3_stability/reports/hit_balloon_part1_1.1/evidence/batch1/r1_blue_a1/scene_snapshots.jsonl
cat v3_stability/reports/hit_balloon_part1_1.1/evidence/batch1/r1_blue_a1/rosout_events.jsonl
```

对这 5 个局（上表列出的那些），把 `scene_snapshots.jsonl` 的时间序列和
`rosout_events.jsonl`／`*mission_once.out`／`observer.out` 对齐，重点看：
- 第二只球消失前后，无人机在做什么（还在飞行任务里，还是任务已经结束在悬停/降落）；
- 有没有边界触发日志、`SPRINT_START`／`Sprint completed`、`[TargetTracker]` 跟踪记录
  刚好发生在那个时间窗口附近；
- 如果第二只球是在任务**结束之后**才从 Actor 列表消失（模式 B、C 都是这样），能不能从
  飞行轨迹（里程计，如果遥测里有）反推出任务进行中无人机有没有靠近过那只球的位置。

**判据**：如果 5 个局都能找到"任务进行中无人机确实靠近过那只非目标球"的证据（哪怕碰撞
销毁的日志本身延迟出现），就支持"误击是真实发生的，只是发现得晚"这个解释，统计口径不用
改，但要在报告里说明真实误击可能比已发现的更早；如果有局找不到任何靠近证据，这就是一个
反例，要单独拎出来，可能指向别的触发机制（比如两只球物理距离太近、UE 自身的碰撞体积
设置问题），不要强行套进"延迟发现"的解释里。

### 第二步：下次试验前确定用什么 GC 策略做"实时"误击判定

`v3_stability/hit_balloon_v2/tools/gc_timing_probe.py` 已经有三种模式：
- `--mode gc`：只在看到 `SPRINT_START` 日志之后才开始按 0.4/1.4/3.0/5.0 秒的节奏发 GC——
  **1.2 已经证明至少 5/9 局根本不会冲刺，这个模式会漏掉所有没冲刺的碰撞**，不要在后面的
  试验里继续用这个模式来判定误击。
- `--mode continuous`：全程按固定间隔（默认 1.5 秒，可调）发 GC + 查询，不依赖冲刺日志，
  1.2 报告里已经验证过可以稳定工作（164 次/0 错误）。**后面 1.6/1.7 的试验都应该用这个
  模式**，这样不管碰撞发生在接近阶段还是冲刺阶段，都能在接近实时的延迟内被发现。
- 1.2 报告里也提醒过："持续发送 GC 本身可能影响仿真时序"——所以继续按 1.2 的做法，
  把这当作一个会影响时序的测量工具来对待，**改前改后的所有验收局都要用同一个策略**，
  不要改前不发 GC、改后发 GC，这样数字才能比。

### 第三步：查有没有办法拿到气球的世界坐标，而不是只有 Actor 数量

`v3_stability/hit_balloon_v2/tools/scene_snapshot.py` 目前只解析 `obj list
class=BP_Balloon_C` 返回的类名和计数，UE 控制台这条命令本身的完整输出里有没有坐标信息
（有些引擎的 `obj list` 输出包含每个 Actor 的 Transform，你可以先直接跑一次这个命令看
原始输出，不一定要改代码）。如果能拿到三个气球的世界坐标：
- 直接算出目标球和两个非目标球之间、以及三个球和三条 `approach_pos`/`goal`（`llm_mission.launch`
  里 A/B/C 三区的那六个坐标）之间的距离，看是不是有哪条接近路径天生离某只非目标球特别近；
- 如果确实很近，这就是"调坐标"能直接解决的问题——现在已经确认改官方 demo 的固定坐标
  不违规（见 `v3_stability/rule_compliance/README.md` 或问主办方的记录），可以放心调。

如果 `obj list` 拿不到坐标，退而求其次，用已有的真实相机帧（`real_frames/`）人工看：
接近/冲刺阶段的画面里，是不是经常能同时看到不止一只气球？能看到就是"路径离得太近"的
视觉证据。

### 第四步：检查识别/跟踪阈值是不是太松

`bt_ros.cpp` 生成的 `TargetTracker` 用的是 `confidence_threshold="0.8"`
（`cross_frame` 阶段的 `TargetLocator` 用的是 `0.7`，两者不是同一个节点，不要混用结论）。
查一下 `TargetTracker` 这个 BT 节点的实现在服务器哪个文件里（这次不算"占用服务器"，
只是只读查看，`grep`/`cat` 即可），看这个阈值具体过滤的是什么——是颜色匹配置信度，
还是纯粹的检测框置信度。如果是前者，阈值 0.8 理论上应该能分开红紫蓝三色，误击更可能是
路径问题而不是识别问题；如果是后者（只判断"这是不是一个气球"，不判断颜色），那误击的
根本原因可能是**系统压根不检查当前跟踪的是不是正确颜色**，这会是一个更根本、更容易修的
问题——**这一步非常值得先查，可能比查坐标还重要**。

## 四、1.7：全量验收

用 1.6 修好的代码，红紫蓝各 ≥3 局（≥9 局），**全程用 `gc_timing_probe.py --mode
continuous`**（见上面第二节第二步），四项指标全部满足才算过：

2. **零误击**（用强制 GC 口径重新量，不要混用旧的"不发 GC"口径）；
3. **零"同局少两只球"**；
4. 边界触发 ≤1/9 局。

和 1.1（改前基线）对比，**必须用同一种 GC 策略重新测一遍 1.1 的基线**（或者至少挑 2–3 局

测量方法换了而站不住脚。

**验收通过标准**：四项指标全部满足，且新旧基线用的是同一种 GC 口径。任何一项没过，
如实报告、按需要回滚，不要为了让数字好看而放宽判据或者偷偷换回宽松的计时口径。

## 附：本提示词的设计意图（给你，不用发给 Astra）

- **把原计划"1.5/1.6"的顺序对调，核心理由是我从她自己产出的数据里挖出了一个她的报告
  没点出来的细节**：五个误击局里，有两种模式（B、C）显示"第二只球"是在任务结束后才从

  这是直接从证据反推出来的风险，不是凭空谨慎。
- **第 4 步（识别阈值是不是真的判断颜色）被标成"可能比查坐标更值得优先查"**：因为如果
  `TargetTracker` 压根不校验颜色，那无论怎么调坐标、怎么调速度曲线，只要飞行路径上出现

  但也可能更容易验证和修复（读代码、加一行颜色校验），值得让 Astra 先查这一条。
- **测量口径一致性被反复强调**：这次新增了"不同 GC 策略测出来的误击数不能直接比较"这条
  纪律，因为如果 1.7 用强制 GC 测出更高的误击数、但 1.1 基线是用旧的 125 秒 settle 口径
  测的，会出现"改了代码之后误击反而变多了"这种假象，其实只是测量方法更灵敏了。不先把
  这件事挑明，Astra 很可能会陷入这种自我怀疑的误判。
