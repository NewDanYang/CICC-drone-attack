## 1. 任务回顾（你布置的）

在不影响基础飞行、不涉及气球的前提下，让 FM9G4B-V **独立**完成方形穿越框、ArUco 标记、起降标识及其他障碍物的识别与定位，结果真正进入原任务链路（正向穿框、ArUco、反向穿框、起降），在完整仿真中验证，并与气球侧一起满足九格多模态 10 分加分条件。ArUco 解码不要求用九格。

## 2. 起点：6.3 方框尝试为什么失败

GPT 给出的 6.3 报告结论是“初始链路失败”。我对照代码和日志找到了原因：

| 现象 | 原因 |
|---|---|
| 调试图里框画在了砖块障碍上，score 0.62（低于 0.70 门限） | `frame_locator.py` 照搬了气球的“问存在 + 遮挡扫描”方法。它适合小而实心的气球；方框大且中间是空的，旁边的砖块也会被答“是”，所以边界找错 |
| TargetLocator 19 次 `Position out of range`，x≈1.83 m（真值 3.25 m） | 官方 TargetLocator 只用框的像素大小估距离。框大了约 1.8 倍，距离就算近了，位置就错了。单元测试能精确复现这组数字 |
| 大模型偶尔回复“好的，请描述您的任务需求。”，不生成命令 | `mission_once.py` 用 `sampling=True` 随机采样；固定种子可复现，说明是采样结果，不是偶发 bug |

## 3. 新方案 v8 是什么

- **识别全部由九格完成**：不用 YOLO、不用 HSV、不用仿真真值。YOLO 只在离线评估时当参照，不进入飞行链路；YOLO 的 `square_frame` 类别在部署时关闭。
- **四类目标**：方形穿越框、方形障碍柱、地面 ArUco 标记、圆形起降标识（场地清单来自 `打击.pdf` §2.1）。
- **定位**：
  - 前视目标（方框、柱子）：距离来自**深度相机** `/rflysim/sensor0/Depth_Cloud`（规则 FAQ：“深度由摄像头（深度相机）给出”）。方框用“边框环”深度，避免中间镂空打到后墙；框的大小必须与深度一致，6.3 那种错框会被这一关挡掉。
  - 下视目标（ArUco、起降标识）：像素射线与地面求交，并补偿姿态。
- **进入原任务链路**：新增一个 BT 节点 `Fm9gLocate`，向九格请求目标，收集 3 个一致的位置样本，写入黑板，再由**原有**的 GoTo / PlanningControl / ArucoDetector / Land 去飞。不改运动控制、不改安全边界、不改速度和航点。
  - 正向穿框：九格定位方框 → PlanningControl 穿越。超时则判失败（不能用预设坐标代替感知，否则违反“禁止指点飞行”）。
  - ArUco：九格先在下视画面找到二维码 → 飞到它正上方 → OpenCV 解码（允许）。
  - 反向穿框：九格重新识别方框；失败时沿用正向感知结果。
  - 降落：九格找起降标识 → 飞到其正上方 → Land。
- **感知窗口**：独立线程显示 “FM9G scene perception” 窗口，并发布 `/fm9g/scene_debug_image`（规则 4.4(5) 要求）。
- **大模型命令生成改为贪心解码**，消除随机性。
- **一键回退**：`rosparam set /fm9g_scene/enabled false` 后，下一局生成的行为树与官方**逐字节一致**（已验证），无需重新编译。另有完整的 `rollback.sh`。

## 4. 服务器验证到哪一步了

另一个有 SSH 权限的代理按 `docs/agent-handoff-fm9g-v8-server.md` 分阶段执行，任何一关不过就停下来交证据，**不自行改算法**。服务器始终保持在基线状态（三个文件 MD5 每次核对一致），没有部署 v8，没有用 v8 飞过。

| 轮次 | 结果 | 我据此做的修改 |
|---|---|---|
| 第 1 轮 | 停在 Gate 1：服务器上的 `mission_once.py` 是不带颜色校验的旧版本，补丁的假设不符 | 改为兼容该版本；测试直接用服务器上那份文件的精确字节 |
| 第 1 轮（附带发现） | **九格原生 `<box>` 输出不可用**：返回固定占位坐标（`400 400 600 600`、`500 500 600 600`、重复 `500 500 500 500`），每次 2–10 s；校验环节正确地全部拒绝了 | 定位方法改为“窗口搜索”：在很多候选窗口上问九格“是否正好框住目标”（单 token 是/否，快且准），由粗到细；找到后只在上次位置附近复测（约 1 s） |
| 第 1 轮（附带发现） | 深度点云抽到一条空消息 | 跳过空消息；无深度时方框退回到“按尺寸估距”（宽高必须一致），柱子只显示不定位 |
| 第 2 轮 | 停在 Gate 1：FM9G 的 `chat()` 要求贪心模式下关闭流式输出，补丁漏了 | 已修复；本地假模型也加上了同样的约束 |
| 第 2 轮（附带数据） | **深度相机可用**：空/满消息交替出现，满消息约 5,100–5,800 个点，悬停时中位点在前方 3.15 m（方框位置）；录到一局基线红色飞行的 243 帧前视（全部带深度）+ 243 帧下视；原版 `mission_once.py` 命令检查 10/10 | — |
| 第 3 轮 | **进行中**。第一次贪心检查超过 10 分钟未结束：关闭采样后 FM9G 默认改用 3 路 beam search 且长度上限很大 | 已改为 `num_beams=1, max_new_tokens=400`，每次检查限时 600 s，代理已在重跑 |

第 3 轮要拿到的是**第一批真实数字**：窗口搜索在真实录像上的识别率、定位误差和耗时；下视相机方向假设是否正确（用二维码在不同位姿下的估计位置是否不动来检验）。

## 6. 已知风险与需要你决定的事

- **耗时**：窗口搜索首次定位方框估计 6–7 s，之后每次约 1 s；每个阶段要 3 个一致样本。整局预计增加十几到几十秒（未实测）。阶段超时已相应放宽（方框 45 s，反向 25 s，ArUco/降落 20 s）。
- **正向穿框超时即失败**：比官方 TargetLocator 无限等待更早暴露问题，但这一阶段若九格不行，就会丢 15 分。
- **柱子**：能识别、显示，但不送给 Ego-Planner（它本来就用深度点云避障）。
- **按尺寸估距的退路**：只有方框可用；框偏大但仍是正方形时挡不住，只能靠期望位置容差兜底（与官方一致）。
- **如果第 3 轮窗口搜索准确率不够**：下一步是按规则允许的 LoRA 微调（官方 FAQ 明确说 demo 的 BBOX 偏差大、需要微调），需要独立人员标注的真实帧。
